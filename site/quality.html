Site Health · Quality Contract

Measure the publication, not just the content.

RESONANCE treats the website itself as a verifiable system: structure is checked before release, managed translations are checked for semantic drift, managed published changes leave append-only version history, browser experience and UI geometry are measured in CI, multilingual screenshots are compared against public main, and the deployed GitHub Pages site is measured again after publication.

Seven layers

Build → Translation → History → Geometry → Browser → Visual → Live Different checks answer different questions.

Principle

No claim without a boundary. No correction without a trail.
RESONANCE Site Health v0.5

1. Publication Contract

The deterministic publication contract builds the journal and checks canonical URLs, structured data, multilingual metadata, sitemap coverage, Market OS evidence boundaries and other release invariants before deployment.

2. Translation Parity Contract

Translation Parity v0.4 manages explicit EN / RU / zh-CN publication triplets. It blocks a release when a managed sibling disappears, locale routing or reciprocal hreflang drifts, or translated articles stop exposing the same evidence/action structure as the English reference.

Parity surfaceRelease ruleWhat it protects
Sibling setManaged EN / RU / zh-CN files all existPrevents a declared localization from silently disappearing.
Locale routinghtml lang, canonical, reciprocal hreflang and visible language switcher agreePrevents readers and crawlers from being sent to the wrong language sibling.
Article outlineH2/H3 levels plus evidence, trajectory, market-question, distribution and source blocks keep the same orderDetects structural translation drift without forcing sentence-by-sentence literalism.
Action surfaceCritical IDs, CTA destinations and runtime script set matchPrevents a localized article from calling a different workflow or losing behavior.
Evidence surfacePrimary / evidence source URLs match the English referencePrevents localization from silently dropping or substituting provenance.

Passing this contract does not prove that translated prose is fluent or nuance-perfect. It proves that the managed localized publication exposes the same structural, action and evidence boundary.

3. Corrections + Version History Contract

Version History v0.5 gives registered publications an explicit temporal identity. A public JSON ledger records version transitions and a human-readable Corrections page exposes what changed, why, which locale/version was affected and which evidence supports the change.

History surfaceRelease ruleWhat it protects
Version chainEvery managed route must form an unbroken initial → current version sequencePrevents ambiguous or skipped publication states.
Append-only historyExisting entries cannot be deleted, reordered or rewritten after v0.5 reaches mainPrevents retroactive rewriting of the correction record.
Published editA modified managed route requires a newly appended event covering that routeBlocks silent edits to version-managed publications.
Change semanticsType + claim impact + reason + before/after versions are requiredSeparates a wording/translation repair from a claim-changing correction.
EvidenceEvery event has inspectable URLs; non-publication updates require RESONANCE GitHub evidenceMakes the correction path independently inspectable.

The initial ledger registers Article #004 and Article #005 across EN / RU / zh-CN. It also records the Article #005 RU/zh-CN parity repair found by v0.4 as a presentation-level localization correction rather than pretending that the underlying English claim changed.

4. UI & Media Contract

Geometry is treated as a release property. New images and controls must satisfy explicit markup rules before the browser audit even starts, and rendered Lighthouse audits re-check the result afterwards.

Imagesalt + positive intrinsic width/heightReserve layout space and keep media understandable to assistive technology.
Local image source≤ 750 KiB per imagePrevent a single editorial asset from becoming a hidden payload regression.
Large imagesrcset when intrinsic width ≥ 960 pxAvoid sending desktop-sized media blindly to smaller screens.

5. Experience Contract

Pull requests that change the publication run Lighthouse against a local build. Representative pages are measured on mobile, with key pages also measured on desktop. The UI Geometry Contract separately records target size, image dimensions, aspect ratio, responsive sizing, contrast and viewport checks.

Performance≥ 80 mobile / ≥ 90 desktopDetect meaningful regressions without pretending a lab score is field data.
Accessibility≥ 95Keep the journal usable across assistive technologies and input modes.
Best Practices≥ 95Catch browser/platform regressions and unsafe defaults.
SEO≥ 95Complement the deterministic SEO contract with browser-level checks.

6. Multilingual Visual Regression

Visual Regression v0.3 captures the homepage, Article #004 EN/RU/中文, Article #005 EN/RU/中文 and this Quality page at three fixed viewports. That gives us 24 candidate screenshots per PR plus public-main baselines and pixel-diff images.

The hard gate blocks horizontal overflow, clipped key text/controls, watched elements outside the viewport and visible primary button targets below 44 × 44 px. Raw pixel-diff percentage remains advisory in v0.3 because legitimate editorial edits also change screenshots.

7. Live Experience Audit

After a successful GitHub Pages deployment, Lighthouse measures the public site again. UI geometry is re-checked against the deployed pages, and the result is stored as an immutable workflow artifact with the audited commit/run context.

Evidence produced

Readable summaries

Compact Lighthouse, UI Geometry, UI Markup, Translation Parity, Corrections History and Visual Regression results are written into GitHub Actions and the PR conversation.

Public history

The human Corrections page and machine-readable JSON ledger expose version transitions and evidence outside the CI interface.

Visual evidence

Candidate, public-main baseline and diff PNGs are retained so layout changes can be inspected rather than guessed.

Versioned rules

Performance, accessibility, localization, correction-history, image, control and viewport requirements live in the repository rather than in tribal memory.

What the numbers do not prove

Lighthouse, UI geometry, translation-parity, corrections-history checks and screenshot diffs are controlled evidence. A passing gate does not prove Google ranking, real-user Core Web Vitals, conversion, nuanced translation quality, factual sufficiency of a correction, visual taste, or identical rendering on every device and network. Those claims require their own evidence.
