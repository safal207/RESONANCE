Transactional Trust Protocol

A framework-agnostic execution protocol for consequential agent actions: keep evidence, authority, shared state, commit preconditions, transport outcomes, external delivery, recovery and final proof connected across the whole transition.

By RESONANCE Research

Derived from Verified Reports #003–#015

Canonical chain

8 stagesObserve · Verify · Authorize · BindCompare · Commit · Reconcile · Prove

Core invariant

trajectory trust > output trustbind proof to the mutation

Agent correctness becomes transactional when software can change shared state, call external systems, retry ambiguous operations and act under permissions that may change while work is in flight.

OBSERVE→VERIFY→AUTHORIZE→BIND
COMPARE→COMMIT→RECONCILE→PROVE

1 · Observe the state that makes the action legal.

Record actor, intent, operation identity, observed state, observed state version and time. A read is a snapshot — not permanent permission.

2 · Verify the evidence behind the observation.

Check value, source, integrity, provenance and freshness. Keep UNKNOWN, ABSENT, COMMITTED and CONFLICT distinct.

3 · Authorize against current trust.

Verify authority identity and binding, activation/revocation lifecycle, trust-registry version and trust-registry freshness. A valid signature can still belong to an authority that is no longer trusted.

4 · Bind the decision to versions.

Carry the observed state version, trust epoch, verification time and invariants into the execution decision. Verified then is not authorized now.

5 · Compare at the mutation boundary.

Require the state version and trust version that authorized the action to still be current. The compare and irreversible transition must be atomic, transactional or otherwise enforced by the mutation authority.

6 · Commit once — and persist delivery intent when the effect is external.

Execute only while bound preconditions hold. If an external side effect cannot share the business transaction, persist a durable delivery intent in that same transaction, then deliver it separately with a stable logical effect identity.

7 · Reconcile ambiguity, database conflicts and transport failures.

UNKNOWN / CONFLICT / DB SIGNAL / ACK UNKNOWN→RECONCILE

A timeout, zero-row mutation, serialization failure, dropped connection or lost external acknowledgement does not prove the intended effect is absent. Retry must re-enter fresh observation and binding; external redelivery should preserve the same logical effect identity when the consumer supports idempotency.

8 · Prove the trajectory.

Preserve state and trust versions, verification decisions, database conflict signals, outbox/delivery identity, transport outcome, external acknowledgement or reconciliation evidence and the final invariant result.

A consequential transition is trustworthy only when evidence, authority, state, commit preconditions, delivery identity, transport outcome, recovery and proof remain connected across the whole path.

Database adapter rule

OBSERVE vN→BIND vN→MUTATION AUTHORITY CHECKS vN

Verified Report #012 moved this rule into a real PostgreSQL service: two connections read the same ABSENT / v100, but a conditional update allowed one writer and converted the stale writer into a safe conflict.

Retry classification rule

0 ROWS / 40001 / OTHER CONFLICT→END STALE TX→RE-OBSERVE
RE-VERIFY→RE-BIND→RETRY ONLY IF STILL LEGAL

Verified Report #013 ran the same two-writer race on PostgreSQL 17.6 at three isolation levels. READ COMMITTED produced a zero-row precondition failure; REPEATABLE READ and SERIALIZABLE produced SQLSTATE 40001. Every losing path reconciled to COMMITTED / v101 / effects=1.

Cross-boundary delivery rule

BUSINESS TX + OUTBOX INTENT→COMMIT→WORKER
STABLE EFFECT ID→EXTERNAL EFFECT→ACK / UNKNOWN→RECONCILE

Verified Report #014 crossed the PostgreSQL-to-external-effect boundary. An unsafe recovery changed request identity after lost acknowledgement and produced two external effects. A transactional outbox preserved delivery intent, stable-id redelivery was deduplicated to one effect, and reconcile-before-retry closed the outbox without a second external call.

Transactional outbox is not universal exactly-once delivery. It removes the database-side lost-intent gap. External uniqueness still depends on an explicit idempotency/deduplication or reconciliation contract.

HTTP transport evidence rule

POST→REMOTE COMMIT→ACK / CONNECTION FAILURE
ACK_UNKNOWN→REMOTE STATUS→FRESH DELIVERY DECISION

Verified Report #015 made the network boundary real with a separate Dockerized HTTP service. The server committed the remote effect, then closed the connection before responding. A new retry identity produced two effects; a real second POST with the same key returned deduplicated; authoritative status reconciliation found COMMITTED and avoided a second POST entirely.

Transport failure is evidence about the connection, not the remote state. When an authoritative remote status interface exists, that observation should drive the retry decision.

Three conformance profiles

FASTTTP-Fast

Low-impact reversible actions: observe, minimal verify, state-version binding, compare/commit, basic proof.

STDTTP-Standard

All eight stages, explicit UNKNOWN/CONFLICT, authority lifecycle, trust freshness, durable evidence, stable external identity and transport evidence where applicable.

DEEPTTP-Deep

Independent verification, stronger provenance, isolated execution, replayable evidence and explicit escalation.

Interpretation boundary

TTP v1.0 is a RESONANCE experimental protocol synthesis. It is not a replacement for database transactions or consensus, not an exactly-once delivery claim, not a PKI/IAM standard, not an OpenAI Agents SDK feature claim and not an external security certification.
